Process Flow Comparison (As-Is vs To-Be) – BABOK-Aligned

You are a senior UX/UI designer and product architect specializing in enterprise business analysis tools (BABOK-aligned).
Your task is to redesign and improve the UX/UI of a Process Flow Comparison screen used by Business Analysts to compare As-Is and To-Be processes.

This is an analysis screen, not a modeling canvas.

1. PURPOSE OF THE SCREEN

The Process Flow Comparison screen supports BABOK analysis tasks, specifically:

As-Is / To-Be Process Analysis

Identification of meaningful differences

Preparation for Gap Analysis and Change Impact Analysis

The screen must help the user quickly answer:

What is different between As-Is and To-Be?

Why is it different?

Which differences require further analysis?

2. TARGET USER

Senior and mid-level Business Analysts

Enterprise / complex environments

Familiar with BABOK concepts

Time-constrained, analysis-focused

The user is interpreting change, not drawing diagrams.

3. UX PRINCIPLES (MANDATORY)

Comparison over creation

Meaning over mechanics

Panels over modals

Progressive disclosure

Clear separation between modeling and analysis

No BPMN purity enforcement

Minimal cognitive load

4. PAGE STRUCTURE (REQUIRED)
4.1 Fixed Process Context Header (Sticky)

Always visible at the top.

Contents

Process Name

Short Process Purpose (1 line)

Comparison indicator:
As-Is (version/date) → To-Be (version/date)

Process Owner / Domain

Last updated timestamp

Rules

Read-only

No editing controls

Establishes scope and orientation

4.2 Comparison Control Bar

Below the header.

Left side

View Mode toggle:

Side-by-Side (default)

Unified (optional future)

Change Filter:

All

Only Changed

Only Added

Only Removed

Right side

Save

Export (Image / PDF)

Compare Settings (icon)

Rules

No modeling actions here

Purely controls how differences are viewed

4.3 Main Comparison Canvas (Dominant Area)

Two panels side-by-side:

Left: As-Is (Current State)

Title: “Current State”

Subtitle: “How the process works today”

Read-only by default

Right: To-Be (Future State)

Title: “Future State”

Subtitle: “How the process is expected to work”

Read-only by default

Visual rules

Reduced grid visibility

Increased whitespace

Unchanged steps visually subdued

Changed steps emphasized via outline, not fill

5. PROCESS STEP INTERACTION MODEL
5.1 Step Selection

Clicking a step must:

Highlight the step

Open a right-hand contextual detail panel

NEVER open a modal

5.2 Step Detail Panel (Right Side)

Persistent, slide-in panel.

Header

Step Name

Step Type badge (Task, Decision, Sub-Process, Manual, Automated)

Change Badge:

Added

Removed

Modified

Unchanged

5.3 Step Detail Tabs (Mandatory)

Tabs must be visible and clearly labeled.

Tab 1: Overview

Step Description

Actor / Role

System involved (if any)

Tab 2: Inputs & Outputs

Inputs

Outputs

Data objects (if known)

Tab 3: Rules & Logic

Business rules applied

Decision logic (if applicable)

Tab 4: Exceptions

Known exceptions

Alternate flows

Tab 5: Change Rationale (MANDATORY FOR NON-UNCHANGED)

What changed?

Why it changed?

Expected benefit

Risks / assumptions

This tab enforces BABOK-aligned reasoning.

6. VISUAL CHANGE SEMANTICS
Color & Style (Restrained)

Added: subtle green outline

Removed: red dashed outline + faded node

Modified: amber outline

Unchanged: neutral gray

No solid fills. No heavy color usage.

7. COMPARISON INSIGHTS PANEL

Replace raw counters with an Insight Summary Panel, placed between or below diagrams.

Examples

“1 manual activity removed”

“Decision logic eliminated”

“Process length reduced by 1 step”

“No new controls added”

These insights must translate structure into analyst-readable meaning.

8. GUIDED ANALYST ACTIONS (NON-INTRUSIVE)

At the bottom or side, show suggested next actions:

Review removed steps for control gaps

Document rationale for modified steps

Create gap from selected change

These are prompts, not enforced workflows.

9. TRANSITION TO GAP ANALYSIS

Clear CTA:

“Analyse Impact → Create Gaps”

This reinforces:

Process Analysis ≠ Gap Analysis

Separation of concerns

Analytical flow

10. EXPLICITLY OUT OF SCOPE

No automatic requirement creation

No BPMN validation enforcement

No dense legend clutter

No diagram-centric UX

11. OUTPUT FORMAT REQUIRED FROM YOU

Produce:

Annotated screen layout description

Component list with responsibilities

Interaction flows (step click, filter change, comparison mode)

UX rationale per major section

Optional wireframe-level ASCII or structured layout

Do not provide implementation code unless explicitly requested.


PROCESS FLOW COMPARISON (UX + FUNCTIONAL SPEC v2)

You are a senior UX architect and interaction designer specialized in enterprise analysis tools.

Your task is to produce a detailed UX + functional interaction specification for a Process Flow Comparison screen (As-Is vs To-Be) used by Business Analysts.

This specification must focus on diagram usability, adaptive layout, focus management, and interaction mechanics, not only visual layout.

1. CORE UX PROBLEM TO SOLVE

Static side-by-side diagrams become unreadable for complex processes.

The system must support:

Adaptive focus

Diagram resizing

Zooming and panning

Step-centric analysis

2. REQUIRED FOCUS MODES

Design the screen to support these modes:

Overview Compare

Side-by-side diagrams

Change overlays visible

Reduced detail

Focus As-Is

As-Is expands to full width

To-Be collapses to narrow reference strip

Focus To-Be

Mirror of Focus As-Is

Step Focus

Selected step auto-centered

Neighbors visible

Other steps dimmed

Describe how the user switches between modes and how transitions behave.

3. DIAGRAM CANVAS BEHAVIOR (MANDATORY)

Specify:

Responsive sizing rules

Minimum readable node sizes

Independent scrolling per canvas

Zoom (wheel, controls, fit-to-view)

Panning (drag)

Auto-centering on step selection

Rule: Content must never shrink to fit a small container.

4. STEP SELECTION & DETAIL INTERACTION

When a step is selected:

Diagram zooms to step

Related steps highlighted

Right-hand detail panel opens

Corresponding step in opposite diagram auto-highlighted

Specify behavior when:

Step exists only in one side

Step is modified vs removed vs added

5. ADAPTIVE PANEL SIZING

Define:

Default split ratios

Drag-to-resize behavior

Collapse/expand logic

Minimum widths

Detail panel overlay behavior

6. ANALYSIS MODE VS EDIT MODE

Define:

Default mode = Analysis

Edit Mode explicitly enabled

Behavior differences per mode

Visual indicators for active mode

7. ACCESSIBILITY & PERFORMANCE CONSIDERATIONS

Include:

Keyboard navigation basics

Visual clarity rules

Performance expectations for large diagrams

8. OUTPUT FORMAT

Produce:

Interaction flow descriptions

State diagrams (textual)

Layout behavior rules

UX rationale per major decision

Do NOT include implementation code.
