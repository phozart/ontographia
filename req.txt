EPIC 1 – System Dynamics Canvas (Core Interaction Layer)
Description

Provide a high-performance visual canvas where users create, move, connect, and edit System Dynamics elements (causal variables, stocks, flows, auxiliaries). This is the foundation for both CLD and stock-flow diagrams.

Feature 1.1 – Canvas Rendering & Navigation

Requirements

Infinite or very large 2D drawing surface.

Smooth pan via click-drag, touchpad drag, or spacebar+drag.

Zoom with mouse wheel + UI buttons.

Zoom-to-fit and zoom-to-selection.

Real-time rendering with no flicker.

Acceptance Criteria

User can pan fluidly at 60fps or similar.

Zoom keeps cursor position centered.

No jitter when dragging many elements.

Canvas state persists on page refresh.

Feature 1.2 – Element Creation Mechanisms

Requirements

Toolbar for adding:

Causal Variable

Link

Stock

Flow

Auxiliary Variable

Parameter / Constant

Text / Note

Right-click menu: quick-add element at pointer location.

Keyboard shortcuts:

"C" = Causal Variable

"S" = Stock

"F" = Flow

"A" = Auxiliary

"P" = Parameter

"T" = Text

Acceptance Criteria

Creating an element takes max. two actions.

Newly created element appears directly under cursor.

Keyboard shortcuts work regardless of zoom level.

Feature 1.3 – Element Manipulation

Requirements

Drag elements with snap-to-grid and alignment guides.

Multi-select via lasso or shift-click.

Duplicate, delete, copy/paste.

Undo/redo stack with minimum 50 steps.

Acceptance Criteria

Dragging multiple nodes maintains relative spacing.

Undo restores exact previous canvas state.

Copy/paste preserves metadata (ID, type, properties).

Feature 1.4 – Element Editing Panel

Requirements

Side panel displaying properties of selected element(s).

Fields vary by type:

Causal variable: label, description, polarity notes

Stock: name, unit, initial value

Flow: name, formula

Aux/Parameter: formula/value

Support Markdown in descriptions.

Autocomplete when linking to domain entities.

Acceptance Criteria

Editing updates reflect immediately on canvas.

Invalid formulas produce inline error messages.

Closing and reopening panel preserves unsaved input until explicitly dismissed.

Feature 1.5 – Links & Connectors

Requirements

Create link via dragging from node output handle to target.

Arrow automatically orients to direction.

Link editing panel:

Polarity (for CLD mode)

Delay toggle

Strength (optional)

Auto-routing to minimize overlap.

Acceptance Criteria

Link creation requires a single drag.

Dragging nodes reroutes link paths dynamically.

Delay indicator renders correctly when enabled.

Feature 1.6 – Canvas Layers

Requirements

Predefined layers:

Structural (nodes + links)

Data/metrics overlay

Annotation layer

Toggle layer visibility individually.

Elements know which layer they belong to.

Acceptance Criteria

Hiding a layer visually removes its elements without affecting layout.

Switching layers does not modify model logic.

Feature 1.7 – Dark/Light Mode

Requirements

Canvas adapts to global app theme.

Node shapes, text, arrows adjust for contrast.

Loop labels and colors remain readable in both modes.

Acceptance Criteria

All diagrams remain legible in both modes.

No color clashes or unreadable elements.

Feature 1.8 – Mini-map

Requirements

Small map showing entire model.

Movable viewport box indicating focus area.

Click/drag inside mini-map to reposition main view.

Acceptance Criteria

Mini-map updates in real time.

Dragging viewport moves main canvas smoothly.

Mini-map autoscaling works for very large diagrams.

EPIC 6 – Simulation-Ready Architecture
Description

Introduce a robust internal representation for stock–flow models (and optionally quantified CLDs) so that models can be validated, parameterized, and executed by a simulation engine in a later phase. This epic defines the data schema, formula language, dependency graph, evaluation rules, and run configuration—all without requiring advanced numerical features up front.

Feature 6.1 – Canonical Model Representation (Simulation Graph)
Requirements

Maintain an internal canonical “simulation graph” derived from the canvas diagram:

Stocks

Flows

Auxiliaries

Parameters

Connectors (dependencies)

Sources/Sinks (optional)

The simulation graph must be buildable from the diagram JSON deterministically.

Store:

Node IDs and types

Units

Formulas and constants

Dependency edges (who depends on who)

Acceptance Criteria

Loading a model produces the same simulation graph every time.

Each flow lists dependencies (aux/param/stock inputs).

Cycles in auxiliary dependencies are detectable.

Feature 6.2 – Run Configuration (Time Horizon & Step)
Requirements

Add a “Run Config” object at the model level:

startTime (number)

endTime (number)

dt (time step)

timeUnit (string, e.g. day/week)

integrationMethod (default: Euler; future: RK4)

UI:

Simple panel for editing run config.

Reset to defaults.

Acceptance Criteria

Default config exists for every model.

Invalid dt (<=0) is rejected with clear message.

Config persists in JSON export/import.

Feature 6.3 – Formula Language (Safe Expressions)
Requirements

Standardize formulas as expressions stored as strings, parsed into an AST (abstract syntax tree).

Supported operations:

Arithmetic: +, -, *, /, ^

Parentheses

Comparators: <, <=, >, >=, ==, !=

Conditional: if(condition, a, b)

Functions: min(), max(), abs(), clamp(x, lo, hi), exp(), log(), sqrt()

Identifiers refer to model elements by stable symbol name resolved to element IDs.

Security:

No arbitrary JS execution.

No eval.

Acceptance Criteria

Parsing detects syntax errors and shows location.

Unknown identifiers are flagged.

AST evaluation works for simple expressions using test variables.

Feature 6.4 – Symbol Table & Naming Rules
Requirements

Each simulation-relevant element has:

symbol (unique within model, e.g. inventory, demand_rate)

displayName (human-readable label on canvas)

Provide auto-symbol generation:

Based on display name

Sanitized to lowercase snake_case

Uniqueness enforced by suffix _2, _3, etc.

UI shows symbol in advanced mode (optional toggle).

Acceptance Criteria

Two nodes with same display name still get unique symbols.

Renaming display name does not break formulas unless user chooses to sync symbol.

Export/import preserves symbols.

Feature 6.5 – Dependency Graph & Topological Ordering
Requirements

Build dependency graph from formulas and connectors:

Aux depends on stocks/params/other aux

Flow depends on stocks/params/aux

Stock update depends on its flows

Compute evaluation order:

Parameters first

Auxiliaries next (topologically sorted)

Flows next

Stocks last (state update)

Detect cycles among auxiliaries:

Provide error message listing the cycle path

Suggest breaking cycle or converting to stock/delay (future)

Acceptance Criteria

Order is stable and reproducible.

Cycles are detected reliably.

Cycle error prevents “Run” (when simulation is enabled later).

Feature 6.6 – Stock Update Semantics (Euler-Ready)
Requirements

Define the stock update equation for later execution:

For each stock:

Stock(t+dt) = Stock(t) + dt * (sum(inflows) - sum(outflows))

Flow values are computed at time t (explicit Euler).

Support multiple inflows/outflows per stock.

Acceptance Criteria

System can compute next-step values for a trivial model (1 stock, 1 inflow, 1 outflow) using internal tests.

Units are not enforced strictly yet, but warnings can appear (from Epic 3).

Feature 6.7 – Initial Values & Reset Behavior
Requirements

Stocks must have an initial value:

Numeric constant OR formula evaluated at t=startTime

Provide “Reset model state” semantics:

Clears runtime state to initial values

Does not modify the design-time model

Acceptance Criteria

Model can restore initial stock values reliably.

Initial value formula errors are reported clearly.

Feature 6.8 – Scenario Parameterization (Simulation-Oriented, Minimal)
Requirements

Overrides parameter values

Feature 6.10 – Simulation API Contract (Internal Interface)
Requirements

Define an internal engine interface (even if not fully implemented):

Input:
