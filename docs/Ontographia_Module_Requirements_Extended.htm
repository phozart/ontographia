Part 1: Design Philosophy and Approach

1.1 Core Design Principles

These modules must embody Ontographia's philosophy: a thinking-first platform that guides users through professional practice while teaching the underlying concepts. The tool should make users better practitioners, not just data capturers.

Principle 1: Guide, Don't Just Capture — Every module should lead users through a structured thinking process with prompts, questions, and suggested sequences. Users should feel guided toward good practice, not abandoned with blank forms.

Principle 2: Teach While Doing — Embed contextual learning throughout. Users should understand why they're capturing something, what good looks like, and how it connects to other concepts. Learning happens through use, not separate training.

Principle 3: Professional Output Quality — Everything produced should be exportable and usable in professional contexts: board presentations, strategy documents, architecture reviews, audit evidence. The tool elevates user output.

Principle 4: Reason About, Don't Operate — These modules help users think about capabilities, services, performance, governance, and risk. They do not manage tickets, route approvals, or execute processes. The boundary is clear: thinking and documentation, not operations.

Principle 5: Integration-Ready — All outputs should be structured for integration with enterprise tools (EA repositories, GRC platforms, strategy tools) and usable as standalone artefacts.

 

1.2 User Experience Pattern

Each module should follow a consistent experience pattern:

Phase

Description

Part 2: Detailed Module Specifications

2.1 Capability and Operating Model Studio

2.1.1 Module Purpose and Context

This module enables explicit modelling of what the organisation must be able to do (capabilities), how it organises to deliver those capabilities (operating model), and who is accountable for what.

💡 Why This Matters

Strategy without capability thinking becomes wishful thinking. Capabilities bridge strategic intent and operational reality by defining what the organisation needs to be good at, independent of how it's currently structured.

 

2.1.2 Teaching Content Requirements

The module must teach users these key concepts through embedded guidance:

Concept

What Users Must Learn

Capability vs Process

A capability is WHAT you can do (an ability). A process is HOW you do it (a sequence of activities). "Customer Onboarding" is a capability. "The 5-step onboarding workflow" is a process. Capabilities are stable; processes change.

Capability vs Function

A capability is an organisational ability. A function is an organisational unit (department). Marketing (function) may own several capabilities. One capability may span multiple functions.

Capability Levels

Level 1: Strategic capabilities (5-12 for most organisations). Level 2: Business capabilities supporting L1. Level 3: Enabling capabilities. Go no deeper than 3 levels initially.

Value Streams

End-to-end flows that deliver value to a stakeholder. Value streams consume capabilities. Map value streams first, then identify required capabilities.

Operating Model

The choices about how capabilities are organised: centralised vs federated, standardised vs customised, insourced vs outsourced. There is no "right" answer — only trade-offs.

 

2.1.3 Guided Workflow

The module should guide users through this sequence (adaptable based on their starting point):

Step 1: Value Stream Identification — "What are the major end-to-end flows that deliver value to your stakeholders?" Guide users to identify 3-8 primary value streams (e.g., Hire to Retire, Order to Cash, Concept to Product).

Step 2: Strategic Capability Discovery — "What must your organisation be exceptionally good at to execute its strategy?" Use prompts like: "If this capability disappeared tomorrow, what would break?" Guide to 5-12 Level 1 capabilities.

Step 3: Capability Decomposition — For each L1 capability, ask: "What component abilities make this up?" Limit to 5-8 L2 capabilities per L1. Warn against going too granular too soon.

Step 4: Capability-Value Stream Mapping — "Which capabilities are consumed by which value streams?" Visualise as a matrix. Identify capabilities that support multiple value streams (shared services candidates).

Step 5: Operating Model Choices — For each significant capability, prompt: "How should this be organised?" Present trade-off dimensions with implications.

Step 6: Accountability Assignment — "Who owns each capability?" Distinguish between accountable (one person), responsible (may be shared), consulted, and informed.

Step 7: Maturity Assessment — "How mature is each capability?" Use a simple scale with behavioural anchors, not abstract numbers.

2.1.5 Common Pitfalls to Guard Against

The module should actively warn users about these common mistakes:

•       Confusing capabilities with departments — Prompt: "This looks like an organisational unit. What ability does this unit provide?"

•       Going too granular too fast — Warn when L3 count exceeds L2 by factor of 10+

•       Capabilities without owners — Flag orphan capabilities during validation

•       Capability names as verbs — Guide toward noun phrases ("Customer Management" not "Manage Customers")

•       Ignoring value streams — Warn if capabilities created without value stream context

2.2 Business Service Management Studio

2.2.1 Module Purpose and Context

This module enables structured reasoning about business services — the bundles of value that the organisation delivers to its consumers. It bridges strategy, architecture, and operations by making services the unit of analysis.

💡 Why This Matters

Organisations think in projects but experience reality through services. When something breaks, users don't care about your architecture — they care that the service is down. This module makes services visible and manageable as first-class entities.

 

⚠️ Important Distinction

This is NOT ITSM or technical service management. We are reasoning about business services (what the business delivers) not IT services (what IT delivers). A business service might be "Customer Account Management"; the supporting IT services are implementation details.

 

2.2.2 Teaching Content Requirements

Concept

What Users Must Learn

Business vs IT Service

A business service delivers business value to a business consumer. "Process Payroll" is a business service consumed by employees and managers. The IT applications supporting it are IT services. Model business services first.

Service vs Capability

A capability is an ability. A service is a packaged offering that uses capabilities. The "Financial Reporting" capability enables the "Monthly Management Reporting" service. Services have consumers; capabilities have owners.

Service Consumer

Who or what consumes the service. Can be internal (other departments, processes) or external (customers, partners, regulators). Different consumers may have different expectations of the same service.

Service Expectations

What consumers expect: availability (when), reliability (how often it works), responsiveness (how fast), quality (how good). These are promises, not SLAs — understand expectations before formalising contracts.

Service Dependencies

What the service depends on: capabilities, other services, systems, data, partners, people. Dependencies create risk. Mapping them enables impact analysis.

 

2.2.3 Guided Workflow

Step 1: Service Discovery — "What services does your organisation provide, and to whom?" Start with external-facing services, then internal. Guide users to name services from the consumer's perspective.

Step 2: Consumer Identification — For each service: "Who consumes this service? What do they use it for?" Build a consumer registry linked to services.

Step 3: Expectation Capture — "What do consumers expect from this service?" Guide through: availability windows, acceptable response times, quality thresholds, criticality.

Step 4: Dependency Mapping — "What does this service depend on?" Walk through: required capabilities, supporting applications, data sources, external partners, key people/skills.

Step 5: Service-Capability Linking — Connect services to the capabilities (from Module 1) that enable them. Validate: "Does every service have at least one supporting capability?"

Step 6: Change Impact Setup — "What happens if this service degrades or fails?" Capture impact on consumers, downstream services, business processes. This feeds risk assessment.

2.2.5 Common Pitfalls to Guard Against

•       Listing IT systems as services — Prompt: "SAP is a system. What business service does it support?"

•       Missing internal services — Remind: "Don't forget services you provide to other departments"

•       Vague consumer definitions — Push for specificity: "Which specific roles or groups consume this?"

•       Expectations without validation — Suggest: "Have you validated these expectations with actual consumers?"

•       Missing dependencies — Prompt: "What external partners or data sources does this rely on?"

 

2.3 Performance and Outcomes Studio

2.3.1 Module Purpose and Context

This module enables structured reasoning about outcomes, measures, and the behavioural effects of metrics. It helps users design measurement systems that drive desired behaviours rather than gaming.

💡 Why This Matters

Bad metrics destroy good strategy faster than bad execution. "Tell me how you measure me, and I will tell you how I will behave." This module helps users think critically about what they measure and why.

 

2.3.2 Teaching Content Requirements

Concept

What Users Must Learn

Outcome vs Output

An output is what you produce (reports generated, calls answered). An outcome is the change that results (better decisions, satisfied customers). Measure outcomes; outputs are just proxies.

Leading vs Lagging

Lagging indicators tell you what happened (revenue, churn). Leading indicators predict what will happen (pipeline, satisfaction scores). You need both, but leading indicators are actionable.

Measures vs Signals

Not everything needs a KPI. Some things are signals — qualitative observations that indicate health. Over-quantifying creates false precision and gaming.

Outcome Chains

Strategic outcomes are achieved through intermediate outcomes. Map the chain: "If we achieve X, it contributes to Y, which enables Z." This validates your theory of change.

Unintended Consequences

Every metric creates behaviour. Ask: "If people optimise only for this number, what might go wrong?" Speed targets reduce quality. Volume targets ignore value.

Goodhart's Law

"When a measure becomes a target, it ceases to be a good measure." Teach users to rotate measures, use baskets of indicators, and maintain qualitative oversight.

 

2.3.3 Guided Workflow

Step 1: Strategic Outcome Identification — "What are you ultimately trying to achieve?" Link to strategy. These are the end states that matter: market position, customer outcomes, organisational health.

Step 2: Outcome Chain Construction — "What intermediate outcomes lead to each strategic outcome?" Build backwards: "To achieve X, we first need Y and Z." Create explicit theory of change.

Step 3: Indicator Selection — For each outcome: "How would you know if you're making progress?" Guide users to identify 2-3 indicators per outcome. Challenge: "Is this leading or lagging? Can you influence it directly?"

Step 4: Unintended Consequence Analysis — For each indicator: "If people optimised only for this, what might go wrong?" Document risks. Design counter-measures (balancing metrics, qualitative reviews).

Step 5: Measurement Feasibility — "Can you actually measure this? At what cost? How often?" Flag indicators that are theoretically good but practically impossible.

Step 6: Feedback Loop Integration — Link to System Dynamics: "How do these outcomes influence each other? Are there reinforcing or balancing loops?"

2.3.5 Common Pitfalls to Guard Against

•       Measuring only what's easy — Challenge: "Is this the right measure, or just the available one?"

•       Too many KPIs — Warn when count exceeds 15-20: "If everything is a KPI, nothing is"

•       All lagging indicators — Flag if <30% are leading: "You're only seeing the past"

•       Missing outcome links — Require each indicator link to at least one outcome

•       Ignoring behaviour — Mandatory: "What behaviour might this incentivise?"

 

2.4 Governance and Decision Design Studio

2.4.1 Module Purpose and Context

This module enables clarity about how decisions get made: who decides what, using what criteria, within what boundaries. Most organisational dysfunction is governance dysfunction disguised as execution problems.

💡 Why This Matters

Unclear decision rights cause delays, conflict, and poor outcomes. People either don't know who can decide, or multiple people think they can. This module creates explicit clarity — not bureaucracy.

 

2.4.2 Teaching Content Requirements

Concept

What Users Must Learn

Decision Types

Strategic decisions (direction, major investments), Architectural decisions (standards, patterns), Operational decisions (day-to-day execution). Different types need different governance.

Decision Rights

The explicit authority to make a decision. Distinguish: who can DECIDE (authority), who must be CONSULTED (input required), who must be INFORMED (after the fact).

Guardrails vs Constraints

Guardrails are flexible boundaries — preferred paths that can be crossed with good reason. Constraints are hard limits — never to be violated. Know the difference.

Escalation Logic

When does a decision need to go up? Based on: financial threshold, risk level, policy exception, cross-boundary impact. Make triggers explicit.

Decision Records

Important decisions should be recorded: what was decided, why, by whom, what alternatives were considered. This enables learning and accountability.

 

2.4.3 Guided Workflow

Step 1: Decision Domain Mapping — "What categories of decisions does your organisation make?" Group by type (strategic, architectural, operational) and domain (financial, technical, people, commercial).

Step 2: Decision Ownership Assignment — For each decision type: "Who has authority to make this decision?" Must be a role, not "the team" or "leadership". One accountable owner.

Step 3: Criteria Definition — "What criteria should guide this decision?" Help users articulate: strategic fit, risk tolerance, cost thresholds, quality standards. Document trade-off preferences.

Step 4: Guardrail vs Constraint Classification — For each policy/standard: "Is this a hard constraint or a guideline?" If guideline: "What's the process for exceptions?"

Step 5: Escalation Path Design — "When should this decision escalate?" Define triggers: financial thresholds, risk levels, policy exceptions, stakeholder impact.

Step 6: Decision Record Template — Create standard format for recording significant decisions: context, options considered, decision, rationale, expected outcomes, review date.

2.4.5 Common Pitfalls to Guard Against

•       Collective ownership — Reject: "The leadership team decides." Push: "Who specifically is accountable?"

•       Everything escalates — Warn: "If most decisions escalate, you've designed bottlenecks, not governance"

•       All guardrails, no constraints — Challenge: "Are there any absolute limits? What can never be compromised?"

•       Criteria-free decisions — Require at least 2-3 documented criteria for each decision type

•       No exception process — If a guardrail has no exception path, it's actually a constraint

 

2.5 Risk and Resilience Studio

2.5.1 Module Purpose and Context

This module enables explicit reasoning about risk, fragility, and organisational resilience. It helps users identify what could go wrong, assess the organisation's ability to withstand shocks, and design appropriate resilience mechanisms.

💡 Why This Matters

In complex systems, optimisation without resilience is dangerous. Efficiency removes slack; slack provides resilience. This module helps users find the right balance and make conscious trade-offs.

 

⚠️ Important Distinction

This is not a GRC compliance tool. We're reasoning about risk to inform decisions — not managing risk registers for audit purposes. The focus is on understanding and designing resilience, not ticking compliance boxes.

 

2.5.2 Teaching Content Requirements

Concept

What Users Must Learn

Risk Categories

Strategic risks (threats to strategy), Operational risks (threats to delivery), Dependency risks (threats from what you rely on). Different categories need different responses.

Single Points of Failure

Places where one failure cascades into major impact: one supplier, one system, one person with critical knowledge. Identifying SPOFs is the first step to resilience.

Resilience vs Efficiency

Resilience requires redundancy, slack, and optionality — all of which reduce efficiency. There's no free lunch. Make the trade-off consciously.

Stress Scenarios

"What if" analysis: What if this supplier fails? What if demand doubles? What if a key person leaves? Scenarios make abstract risks concrete.

Resilience Mechanisms

Ways to build resilience: redundancy (backup options), diversity (different approaches), modularity (contained failure), adaptability (ability to change). Each has costs.

Risk Appetite

How much risk is acceptable? This varies by domain. An organisation might accept high innovation risk but low safety risk. Make appetite explicit per domain.

 

2.5.3 Guided Workflow

Step 1: Risk Domain Definition — "What domains of risk matter for your organisation?" Typical: Strategic, Operational, Financial, Compliance, Reputational, Technology. Customise to context.

Step 2: Risk Identification — For each domain: "What could go wrong?" Use prompts: capability failures, service disruptions, dependency breaks, external shocks. Link to capabilities and services from other modules.

Step 3: Single Point of Failure Analysis — "Where are there no backups?" Walk through: key people, critical systems, sole suppliers, unique data sources. Flag anything where loss = significant impact.

Step 4: Impact and Likelihood Assessment — For significant risks: "How bad would it be? How likely is it?" Use qualitative scales with behavioural anchors, not false precision.

Step 5: Stress Scenario Development — "What scenarios should we think through?" Create 3-5 meaningful scenarios that stress different parts of the organisation. Not worst-case-everything, but plausible severe events.

Step 6: Resilience Mechanism Design — For priority risks: "How do we build resilience?" Options: prevent (reduce likelihood), prepare (reduce impact), respond (recover faster), adapt (change approach).

Step 7: Integration with System Dynamics — Model how risks interact and propagate. "If A fails, what happens to B?" Build causal understanding, not just lists.

2.5.5 Common Pitfalls to Guard Against

•       Risk register mentality — This is not about maintaining lists for audit. Focus on understanding, not documentation.

•       False precision — Warn against precise probabilities: "You don't know it's 23% likely. Is it rare, occasional, or frequent?"

•       Ignoring dependencies — Every risk should link to affected capabilities/services

•       All prevention, no resilience — Challenge: "What if prevention fails? What's your recovery plan?"

•       Static analysis — Risks evolve. Build in review triggers and connect to System Dynamics for dynamic modelling.

Part 4: User Interface and Experience Requirements

4.1 Guided Experience Patterns

The interface must guide users through professional practice. This section specifies required guidance mechanisms.

4.1.1 Contextual Help System

•       Every field should have contextual help explaining what it is and why it matters

•       "Learn more" links to deeper educational content

•       Examples of good vs poor entries

•       Warnings about common mistakes, triggered contextually

 

4.1.2 AI-Assisted Guidance

•       Socratic questioning to help users articulate what they know

•       Suggestions based on what's already captured ("Based on this capability, you might also need...")

•       Completeness prompts ("You have services without consumers defined")

•       Consistency checks ("This capability is marked critical but has no risks identified")

•       Quality coaching ("This description is very brief. Consider adding...")

 

4.1.3 Progressive Disclosure

Start simple, reveal complexity as needed:

•       Basic mode: Core fields only, most users most of the time

•       Advanced mode: Additional fields, relationship details, extended attributes

•       Expert mode: Full metadata, integration configuration, bulk operations

 

4.2 Visualisation Requirements

4.2.1 Interactive Diagram Features

•       Click-to-drill: Select any element to see details or navigate to related items

•       Filter and highlight: Show/hide elements by attribute, highlight paths

•       Layout options: Auto-layout plus manual adjustment capability

•       Export at quality: Vector formats for print, raster for presentations

•       Annotation: Add notes, highlights, callouts for presentation

 

4.2.2 Dashboard Views

•       Module home: Summary of content, completeness indicators, recent changes

•       Cross-module: How entities in this module connect to others

•       Health indicators: Data quality, coverage gaps, staleness warnings

 

4.3 Teaching Integration

Learning should be embedded, not separate:

•       Concept cards: Brief explanations of key concepts, accessible in context

•       Practice guides: Step-by-step workflows for common tasks

•       Examples library: Real-world examples users can browse and learn from

•       Anti-pattern warnings: "This looks like [common mistake]. Did you mean...?"

•       Progress tracking: "You've completed capability mapping. Consider moving to value streams."

 

Part 5: Explicit Exclusions

Ontographia reasons about how organisations operate. It does not operate them. These exclusions define the boundary.

5.1 What These Modules Must NOT Do

Excluded Capability

Rationale

Task management / work tracking

Belongs in project management tools. Ontographia defines what needs doing, not tracks its execution.

Incident management

Belongs in ITSM tools. Ontographia reasons about service design, not operational incidents.

Approval workflows

Belongs in workflow tools. Ontographia defines governance, not executes it.

Real-time dashboards

Belongs in BI tools. Ontographia defines what to measure, not displays live metrics.

Process execution / BPM

Belongs in BPM tools. Ontographia reasons about process design, not runs processes.

Compliance evidence collection

Belongs in GRC tools. Ontographia defines governance, not collects audit evidence.

Risk treatment action tracking

Belongs in GRC/project tools. Ontographia identifies risks and designs resilience, not tracks remediation tasks.

 

5.2 The Boundary Principle

When in doubt, apply this test: "Does this help users THINK about their organisation, or does it help them OPERATE their organisation?"

•       If THINK → include it

•       If OPERATE → exclude it, but ensure good export to operational tools

 

Ontographia is the place where thinking happens. Other tools are where action happens. The integration layer ensures thinking informs action.

6.2 Implementation Priorities

Recommended build sequence based on dependencies and value:

Phase 1: Capability and Operating Model Studio — Foundation for all other modules. Most organisations need this first.

Phase 2: Business Service Management Studio — Depends on capabilities. Bridges to operations.

Phase 3: Performance and Outcomes Studio — Can start in parallel. Needs strategy integration.

Phase 4: Governance and Decision Design Studio — Benefits from capability and service context.

Phase 5: Risk and Resilience Studio — Richest when capabilities, services, and governance exist.

 

6.3 Success Criteria

These modules are successful when:

•       Users can complete a capability model without prior training — the tool taught them

•       Exports are immediately usable in professional settings without reformatting

•       Users make better organisational decisions because they thought through the domain

•       The tool feels like a thinking partner, not a data entry system

•       Integration with existing Ontographia modules feels seamless and natural

 

With these modules, Ontographia becomes a complete organisational thinking platform: from strategic intent through operational design to measured impact, with resilience and governance woven throughout.
