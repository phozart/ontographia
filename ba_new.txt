3. Formal meta-model (diagram specification)
3.1 Core abstract entities
[Requirement] (abstract)
  - requirementId
  - title
  - description
  - rationale
  - owner
  - status
  - acceptanceLogic

[Delivery Item] (abstract)
  - deliveryId
  - title
  - owner
  - priority
  - risk
  - status

[BA Artefact] (abstract)
  - artefactId
  - type
  - description
  - location


These three are separate roots.
No inheritance between Requirement and Delivery Item.

3.2 Requirement specialisation (semantic hierarchy)
[Business Requirement]
    └─ specializes Requirement

[Stakeholder Requirement]
    └─ specializes Requirement

[Solution Requirement]
    └─ specializes Requirement
        ├─ [Functional Requirement]
        └─ [Non-Functional Requirement]

Relationships
Business Requirement
    1 ── refines ──> 0..* Stakeholder Requirement

Stakeholder Requirement
    1 ── refines ──> 0..* Solution Requirement


This is the only true hierarchy in the model.

3.3 Delivery model (non-semantic hierarchy)
[Epic]
    └─ specializes Delivery Item

[Feature]
    └─ specializes Delivery Item

[User Story]
    └─ specializes Delivery Item

Relationships (delivery only)
Epic
    1 ── decomposes into ──> 0..* Feature

Feature
    1 ── decomposes into ──> 0..* User Story


This hierarchy has no semantic meaning about requirements.

4. Cross-domain traceability (the critical part)
4.1 Requirement → Delivery relationships

These relationships are many-to-many and mandatory.

Epic
    ── implements ──> 1..* Business Requirement

Feature
    ── realises ──> 1..* Stakeholder Requirement
    ── realises ──> 0..* Solution Requirement

User Story
    ── operationalises ──> 1..* Functional Requirement

Non-Functional Requirement
    ── constrains ──> 0..* Epic
    ── constrains ──> 0..* Feature


Important rule (encode this explicitly):

A delivery item cannot exist without at least one linked requirement.

5. BA artefacts linkage (supporting layer)
5.1 Artefact specialisation
[Capability Map]
[Business Information Model]
[Process Model (BPMN)]
[Use Case Diagram]
[Context Diagram]
[NFR Catalogue]
[Mock-up / Wireframe]


All specialize:

BA Artefact

5.2 Artefact relationships
BA Artefact
    ── explains ──> Requirement

BA Artefact
    ── supports ──> Delivery Item


Rules:

Artefacts never satisfy requirements

Artefacts never replace requirements

Artefacts exist to clarify, validate, or elaborate

7. Why this meta-model works (and yours already hinted at it)

BABOK logic remains pure and defensible

Agile delivery remains flexible and pragmatic

Traceability is explicit, not implied

You avoid the industry anti-pattern of:
“User stories as requirements”

This model scales cleanly to:

EA viewpoints (later)

Jira / Confluence integration

Knowledge graph implementation (Neo4j fits perfectly)
